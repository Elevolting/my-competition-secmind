# SecMind 学习 ARTEX 的路线与实施计划

## 执行版 Plan（2026-10-15）

### 目标

从 ARTEX 提取可复用的数据契约、状态机、证据链和故障处理方式，接入 SecMind 现有的 Python、FastAPI、React、模型网关、账本和 MCP 体系。优先移植设计和验收场景；只有职责单一、依赖少且许可证确认清楚的代码才考虑直接复制。

### 学习范围与优先级

| 阶段 | 学习主题 | 交付目标 | 进入下一项的条件 |
|---|---|---|---|
| P0 | 执行检索、流量证据、独立复核 | 从一次执行定位观察，固定原始请求／响应，独立复核并保留新旧证据 | 记录、证据、发现、报告和复核历史可以相互追溯；失败、缺件、截断有明确状态 |
| P1 | 跨任务资产、跨轮规划、技能统计、旁路问答 | 复用资产和规划状态；区分技能加载与真实调用；运行中提问且不影响主任务 | 资产范围隔离、待办依赖可恢复、统计可回到原事件、问答可回到提交时快照 |
| P2 | 冷节点摘要、归档恢复、事件通知、ScopeSentry 同步 | 支撑长期运行、备份迁移、站内提醒和外部资产导入 | 原记录可展开；归档清单和哈希可校验；通知去重重试；同步先预览再导入 |
| 条件项 | 审批上下文、模型池健康状态 | 先复现现有缺口，再决定是否实现 | 只有在差距审计证明有实际收益时立项 |

### 每个里程碑的固定流程

1. **源码对照：**记录 ARTEX 文件、版本或 SHA256、许可证、可学习设计和不直接照搬的部分。
2. **契约设计：**先定义实体、状态转换、关联键、幂等键、权限边界和迁移；旧数据行为必须明确。
3. **最小实现：**接入现有服务和页面，避免另起一套存储、Planner 或模型调用路径。
4. **故障验收：**覆盖并发、重试、取消、迟到回调、服务重启、权限越界、缺件和重复请求。
5. **交付记录：**补操作说明、测试证据、限制和来源声明；通过后独立提交并推送。

### 代码移植规则

ARTEX 根目录为 AGPL-3.0。直接复制任何 Go 或前端代码前，必须逐文件记录来源路径、版本、修改点、版权和许可证；`web/LICENSE` 不能推导整个仓库都是 MIT。没有必要复制的部分采用 Python／React 重写，保留 ARTEX 的行为契约和验收场景。

### M1 已完成的工作与验收

实现位于 `an/src/security_agent/asset_library.py`、`asset_library_api.py` 和 `an/frontend/src/app/AssetLibraryPage.jsx`。相关后端 26 项、前端 55 项、生产构建和浏览器交互验收通过；全量后端回归 746 项通过、4 项跳过，随后新增的状态回归已单独通过。Ruff／mypy／Bandit 与提交基线对比无新增问题。浏览器夹具已修复弹窗动画期间输入焦点和 Select 点击方式，并检查搜索响应乱序、错误重试及任务跳转。

1. **审查现有草稿：**核对身份规范化、并发同步、失败重试、历史观测保留及非 URL 范围展示；明确查询参数与 HTTP 方法是否参与身份，避免把不同操作的覆盖状态错误合并。
2. **完成数据契约：**全局资产只承担身份；任务关联保存来源、授权范围、观测和发现引用。查询值不进入全局身份或列表展示。覆盖仅由成功的显式观测产生，资产关联不授予其他任务执行权限。
3. **接通页面：**提供关键词、资产类型、任务和观测状态筛选；详情展示任务来源、范围、关联发现，并能跳回原任务。验证窄屏布局。
4. **验收后独立提交：**覆盖跨任务同端点、不同范围、重复同步、失败观测、精确发现关联、敏感查询值和并发；运行相关后端检查、前端测试和生产构建。

`observed` 仅表示该任务存在成功的显式观测，不表示同一端点的全部 HTTP 方法、参数或漏洞类型均已测试。页面统计与后续规划必须沿用这一含义。

### M3 技能统计：代码落点与工作包

ARTEX `server/skill_usage.go` 的 `meteredSkill` 在调用底层 `Skill()` 前写入加载请求记录；`found=false` 表示技能不存在，`found=true` 只表示注册表命中，不能证明底层加载已经成功。这一设计值得学习的是事件留痕与按任务、角色聚合。SecMind 应在真实加载返回或异常边界区分成功、失败；签名校验失败、实际工具调用和调用失败各自保留明确的事件含义。

| 顺序 | 工作包 | SecMind 落点与要求 |
|---|---|---|
| 1 | 明确真实事件源 | 审计 `secmind/src/secmind/skill_registry.py:load()`、`external_skills.py:compile_binding()` 和 `orchestrator.py` 的加载路径，区分首次上下文加载与执行前的包核验；`selected_skill_ids` 只代表选中，不能算成功加载 |
| 2 | 定义可追溯事件 | 保存事件编号、任务／步骤／attempt、技能及版本、角色、事件类型、结果、来源回执和时间；加载失败记录原因，秘密值不进入统计；缺少归属时明确保留未知值 |
| 3 | 接入加载与调用 | 加载事件在真实加载返回或异常边界产生；实际调用接入 `tooling/broker_execution.py` 的 `tool.invoke()` 边界，在领取、授权和 dispatch permit 校验后记录。缓存命中、正在执行、需要恢复及授权拒绝不能计实际调用；DAG 回执用于关联和投影。依据已核验 work contract 和工具绑定保存候选技能、版本、角色及归因依据，缺失时保留未知值 |
| 4 | 持久化与跨服务查询 | 复用账本及 `tooling/broker.py:_append()` 的 fenced outbox、coordinator 事务；实际调用以任务、逻辑调用标识、ExecutionStore／UnitOfWork 返回的 invocation attempt 和事件类型去重，不直接用 `ToolContext.attempt` 代替调用 attempt。审计现有 started／completed／failed 去重键对真实重试的适配；独立服务扩展现有 `/api/v1/skills` 相关查询，工作台通过 `secmind_adapter.py` 映射远端任务，不另造一份调用事实 |
| 5 | 统计页与验收 | 工作台提供加载成功、加载失败、实际调用及调用结果的筛选和事件详情；可跳回原任务与回执。验证事件重放、真实重试、加载未调用、多个技能和未知归属 |

聚合接口先明确每个指标的分母。一次工具调用即使关联多个技能，任务总调用数也只算一次。没有可靠的发现关联时，不展示“技能漏洞检出率”或“技能成功率”。

加载事件也必须有稳定的操作身份：同一恢复／重放不新增事件，重新进行的一次真实加载或核验使用新操作编号。上下文加载与执行前包核验分别标记用途。`_bind_work_contract()`、`_primary_agent_work_contract()` 是同步入口，事件接入需沿用现有持久化和 fencing 契约，不能仅在异步主循环里补记录。

M3 验收至少覆盖：加载成功但未调用、技能不存在、包校验失败、缓存命中、重复事件、真实重试、授权拒绝、多技能绑定、未知归属、服务恢复和迟到租约。聚合结果必须能回到原事件；工具开始后尚无结果显示进行中或结果未知，不能直接判为成功或失败。

**M3 本地验收结果（2026-10-15）：**引擎相关回归 79 项通过，随后新增真实执行契约整合测试 2 项通过；工作台桥接 9 项通过；前端 55 项、生产构建、浏览器筛选／分页／重试／跳转和窄屏布局通过。实际调用只接独立引擎 `tool.invoke()` 边界，工作台通过远端任务引用查询，不从 Runtime 选择技能或 Pi 日志推算事实。跨服务覆盖、outbox 延迟、旧任务和 O(N) 聚合限制已写入操作说明。M4 已在后续里程碑完成，M5–M8 仍待实施；M3 完成不代表整个学习计划完成。

### M4 旁路问答：代码落点与工作包

重点阅读 ARTEX `sidequestion/capture.go`、`context.go`、`service.go` 和 `README.md`。可借鉴的核心是实际模型请求边界的结构化快照，以及问答的独立状态与取消。

| 顺序 | 工作包 | SecMind 落点与要求 |
|---|---|---|
| 1 | 审计模型边界 | 核对两侧 `llm.py` 及独立服务 `model_gateway/transport.py`；选定实际主任务请求入口，记录最终模型身份、消息及生成参数。工具调用与工具结果必须配对，摘要请求不覆盖主快照 |
| 2 | 持久化快照 | 快照记录父任务／Worker、版本、时间和来源引用；固定提交时版本，限制可查询字段及范围；不从 UI 日志重建模型上下文。旧任务无快照时展示不可提问及原因 |
| 3 | 独立请求生命周期 | 问答复用现有模型网关和用量回执，使用独立预算、幂等请求编号、并发上限与取消状态；关闭面板或断开事件连接不取消请求。主任务执行器保持原控制流程 |
| 4 | 历史与恢复 | 持久保存累计回答、状态、用量和递增事件序号；服务恢复将遗留运行请求标记为中断，保留已保存内容，避免自动重放付费请求；清空后拒绝迟到回调 |
| 5 | 页面与验收 | 任务／执行详情增加问答入口、历史、停止按钮和快照时间；覆盖主任务并行、独立取消、刷新重连、重复提交、预算耗尽、无快照和服务恢复 |

首版仅回答快照中的问题，不提供工具执行入口。长上下文先按预算限定旁路副本，后续与 M5 的摘要能力对接；摘要不改写原任务事实。

**M4 请求边界初审记录（2026-10-15，描述草稿接入前的基线）：**工作台 `an/src/security_agent/llm.py:_request_with_retry()` 在加入 JSON Schema、最终模型、流式参数后发出 HTTP 请求；初审时 `structured()` 没有显式任务编号，任务归属存在于编排器传入的事件观察闭包中。快照接入应增加明确的任务／调用身份或受限 capture scope，在真实发送前复制最终请求，不能用观察事件文本重建。模型探测、embedding 和旁路自身请求不发布主快照。

独立引擎的实际发送点在 `secmind/src/secmind/model_gateway/transport.py:request_with_retry()` 的 `client.stream()` 前，已有 `run_id`、logical call、模型、最终 payload 和 lineage。其 HTTP 响应目前通过 `read_bounded_response()` 收齐后解析；旁路部分回答的持久化需要独立流式消费实现，不能声称复用现有读取就已支持增量保存。`lineage_stage` 用于区分主请求、修复和 fallback，不能单独承担主任务／旁路／摘要用途判定。

下一工作包先确定三个契约：① 父任务与执行步骤的稳定身份；② 明确主请求用途、冻结版本和允许读取的快照内容；③ 独立旁路请求、预算预留／结算和模型配置身份。两侧现有主任务用量不能直接归到旁路，也不能通过伪造主任务编号混入计费。首版仅为取得真实快照的任务提供入口；外部 Runtime／Pi Worker 没有对应模型请求快照时明确不可用，后续通过真实执行边界扩展。

**M4 实施顺序与评审产物：**

| 子项 | 要学习与实现的内容 | 可审查的交付 |
|---|---|---|
| M4.1 | 显式区分主请求、摘要、探测和旁路；在实际发送前深拷贝最终 payload | 快照契约包含父任务／步骤／Worker、调用编号、版本、时间、来源、最终模型与配置身份；MockTransport 证明内容对应真实发送参数 |
| M4.2 | 使用独立问答 identity 与状态，不进入主任务工具循环 | 独立表、幂等请求、预算预留／结算、并发限制；配置变化拒绝旧快照，凭据仅在请求时读取 |
| M4.3 | 累计输出落库、取消和清空的迟到写入保护 | 递增事件序号与清理版本；重启把遗留运行请求标记为 interrupted，保留部分回答与已知用量，不自动重放 |
| M4.4 | 按真实快照来源路由到工作台或独立引擎 | 任务／执行详情面板、历史、停止、快照时间；无快照时展示原因；关闭面板、刷新与断开连接不取消请求 |
| M4.5 | 完成故障回归和操作说明 | 已完成：重复 ID、不同问题冲突、预算不足、并发、独立取消、重启、清空后迟到响应、刷新重连及配置变化；操作说明见 `artex-side-question-operations.md` |

首版快照描述最近一次真实发送请求；若尚未实现完整回复／终态快照，页面必须明确该边界，不能声称包含最新全部进展。工具消息保持调用与结果配对；超出上下文限制时调整旁路副本或明确拒绝。输出 token 设置上限；缺失 provider 用量标记为未知，不能把未知费用记为零。摘要、重试及恢复行为都需要纳入同一旁路预算。

数据库兼容沿用各服务既有方式：工作台处理新增表与旧数据，独立引擎增加 Alembic migration 并验证 production／competition 的 migration head；仅在开发环境 create_all 不构成生产交付。

| 事件通知 | 持久投递状态、去重、失败重试 | 同一事件不重复展示，失败可重试且有投递记录 |
| ScopeSentry 同步 | 外部资产映射、预览、来源与范围约束 | 导入前可预览差异；越权目标不入库，重复导入不产生重复资产 |
| 审批上下文与模型池（条件项） | 决策输入快照、故障类型及流式输出边界 | 先复现当前缺口；审批资料脱敏可追溯，故障切换不得重复已输出内容或重复计费 |

现有的任务级资产图、审批、预算、模型用量和 MCP 接入可作为基础，不安排整套重做。每项开始前先核对 ARTEX 数据模型与 SecMind 的现有契约，再确定最小接口变更和回归范围。

## 第二、三期交付顺序

1. **跨任务资产库：**先定义规范化身份、任务关联、来源和授权范围，再迁移现有资产引用；以同一资产跨任务出现、范围不同和重复导入做回归。覆盖率仅由明确的测试观测产生，不用调用次数代替。
2. **持续规划对照：**用串行三步和两个独立分支复盘现有 Planner；检查前置事实、失败、取消及重启。只为验证出的缺口补持久待办或依赖约束。
3. **技能统计和旁路问答：**分别交付独立 API 与页面；统计取真实加载／调用事件，问答固定快照、单独预算、取消和来源引用。
4. **冷节点摘要和归档：**先建立可展开的原记录引用，再定义带版本、清单和哈希的归档格式；恢复在隔离库中验证幂等与完整性。
5. **通知和 ScopeSentry：**通知先做站内持久投递；资产同步先做差异预览和范围校验，再允许正式导入。两项分别完成失败重试和重复请求回归。

每个里程碑独立提交实现、数据迁移、必要的回归和操作说明；前一项验收失败时不标记后一项完成。条件项只在差距评估证明收益后立项。

## 第一期实施设计

### 1. 统一执行记录与检索

- 统一关联 `run_id`、模块、Worker、意图、执行尝试、步骤、工具、时间和结果状态。
- 接入统一平台账本、MCP 调用回执及 Runtime 发布的执行事件；为 Pi、Claude 适配器补充公开执行输出的持久记录。
- 查询采用“短摘要命中 → 按步骤读取详情”。检索默认限制在当前任务；Worker 通过服务器绑定的任务上下文访问记录。
- 执行内容先脱敏，再持久化和建立检索投影。首期使用数据库关键词匹配与游标分页，支持 SQLite、PostgreSQL。
- 历史回填仅处理项目自身保存的账本和回执；缺失内容显示“记录不可用”。账本是权威来源，检索投影可重建。
- 前端在执行详情增加搜索、模块／Worker 筛选和跳转到原始步骤的入口；Agent 获得同等范围的只读检索工具。

### 2. 流量证据快照与绑定

- 首期支持平台 HTTP 工具结果、Burp 历史，以及通过现有上传入口提交的 HAR。Yakit、Reqable 专用适配列入后续扩展。
- 保存来源回执、时间、方法、URL、状态码、请求／响应、内容摘要和哈希；记录缺失或截断状态。
- 证据角色采用 `baseline`、`proof`、`verification`、`supporting`，分别表示正常对照、漏洞证明、复测和辅助材料。
- 使用现有 `Evidence` 与 `Finding.evidence_ids` 建立关联；绑定操作写入账本，报告展示证据编号、来源与完整性。
- 快照保存到项目管理的证据目录。绑定事务只引用已写入并校验的文件；删除工具历史不会破坏已绑定证据。
- 固化前遮蔽认证头、Cookie 和明确的密钥字段，保留脱敏标记；正文不执行。查看和导出采用同一脱敏版本。
- 前端提供请求／响应查看、证据角色标注、完整性提示及脱敏导出。证据绑定本身不提升发现的可信等级。

### 3. 全模块独立复测／复核

采用统一复核记录，按模块调用不同执行策略：

| 模块 | 执行方式 | 结论与证据门槛 |
|---|---|---|
| Web／渗透 | 在原授权范围内，针对单个发现执行最小 PoC，并采集正常对照 | `reproduced / fixed / inconclusive`；“已修复”须有可比前置条件、原触发检查和正常对照 |
| 代码审计 | 对原缺陷位置、相关调用链和验证规则进行定向复核；支持上传修复版本 | 同上；只有原路径被覆盖且验证支持修复时才能判定 `fixed`，无命中本身不足以证明修复 |
| 逆向分析 | 对选中的行为、函数、解码结果等结论重新取证；记录样本哈希 | `supported / refuted / inconclusive`；结论须关联本次生成的证据 |
| 日志分析／应急研判 | 对指定事件、时间范围、因果判断或处置结论重新分析材料 | 同上；关键材料缺失、时间范围不完整时判为无法确认 |

共同规则：

- 发起时冻结原发现／结论、证据、输入哈希及约束，创建独立子任务、预算和执行记录。
- 服务端根据来源模块选择策略。代码和材料分析增加结构化的复核目标，由执行器限制范围。
- 支持复用原输入或通过既有上传入口提交新版本；新目标必须落在原授权范围内。
- 网络策略和高风险操作沿用现有审批。需要新登录态时使用当前配置，历史凭据不自动重放。
- 同一来源对象同时只允许一个活动复核；重复请求返回已有记录。取消、超时、服务重启均保留已生成证据。
- 结论必须引用本次执行证据，经过服务端验证后保存。历史证据用于比较，不能充当本次验证结果。
- 原报告保持为历史快照；最新复核结论单独展示，并纳入报告刷新。复核失败不改写原结论。
- 前端从发现或结论详情发起，展示独立进度、前后证据差异和历次结果。

## 接口、兼容与交付顺序

新增接口统一置于 `/api/v1`：

| 接口 | 用途 |
|---|---|
| `GET /runs/{run_id}/traces` | 按关键词、模块、Worker 和游标检索 |
| `GET /runs/{run_id}/traces/{trace_id}` | 读取执行记录详情 |
| `POST /runs/{run_id}/traffic-evidence` | 从工具回执或已上传 HAR 固化证据 |
| `GET /runs/{run_id}/traffic-evidence/{evidence_id}` | 查看证据快照 |
| `POST /runs/{run_id}/findings/{finding_id}/traffic-bindings` | 绑定证据及用途 |
| `POST /runs/{run_id}/retests` | 针对发现或报告结论发起复核 |
| `GET /runs/{run_id}/retests` | 查看复核历史 |

复核请求包含来源对象引用、补充说明、可选上传引用和独立预算；返回复核编号及子任务编号。进度、审批、取消和事件订阅复用现有子任务接口。报告结论使用冻结快照中的稳定引用。

新增字段采用可选值和默认值，旧任务继续可读。新增表沿用各服务的数据库兼容方式；独立引擎提供 Alembic migration，生产启动继续检查 migration head。历史投影回填可重复运行。

首期已按四个可审查里程碑交付：**记录与检索 → 流量证据 → 各模块复核执行与验证 → 前端闭环及文档**。检索、流量证据和复核均有独立回归；跨接口测试覆盖“执行记录 → 证据绑定 → 独立复核 → 报告追溯”。第二期资产库、跨轮规划、技能统计和旁路问答已完成本地验收，下一步进入 M5 冷节点摘要。真实授权目标与外部模型的联调属于后续运行环境验收，不计入本地固定材料结论。

## 测试与验收

- **检索：**不同 Worker 的记录能命中并跳转；重复同步不重复入库；任务隔离正确；完整输出、截断和缺失状态准确；敏感字段不进入检索结果。
- **证据：**HAR 和工具回执能固化并绑定；哈希可验证；删除源历史后仍可读取；文件损坏、缺失或跨任务引用会明确失败。
- **Web／代码复测：**覆盖仍可复现、确有修复、登录失效、目标不可达、验证路径未覆盖等场景，后三类不能误报修复。
- **逆向／日志／应急复核：**覆盖支持原结论、证据推翻结论及材料不足；每个有效结论能回到本次证据。
- **生命周期：**覆盖重复点击、并发提交、取消、预算耗尽和服务重启，避免重复执行或改写历史。
- **回归：**运行相关 Python 测试、前端测试与构建，并核对既有审批、任务恢复和可信报告行为。

最终验收：在本地固定测试环境中，能够从执行记录找到观察，将其绑定到发现或结论，发起独立复核，并在报告中追溯原证据、本次证据及判定依据。首期验收不依赖外部真实目标或付费模型。
