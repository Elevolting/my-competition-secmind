# Java Security-Sensitive Randomness Review

## Strategy Intent
Determine whether predictable randomness is used to generate a value whose unpredictability is a security requirement.

## Apply This Strategy When
- CWE-330 is targeted and `Random`, deterministic seeds, weak generators, token/nonce/session generation, or security-sensitive sampling is visible.

## Do Not Use It To
- Report non-security simulation, UI variation, load balancing, randomized tests, or ordinary sampling as a vulnerability.
- Assume every `SecureRandom` use is safe without checking seeding/reuse when visible.
- Require attacker control of the generated value.

## Analysis Procedure
1. Identify the generator, seed source, and exact generated value.
2. Establish the security purpose: authentication/session token, password-reset code, cryptographic nonce/key, CSRF state, identifier secrecy, or another unpredictability requirement.
3. Trace generated bytes/numbers through encoding, truncation, range reduction, and reuse.
4. Evaluate deterministic/default seeding, timestamp seeds, small output space, repeated nonce risk, and predictable transformations where evidenced.
5. Check whether a secure generator supplies the value on the reachable production path.
6. Distinguish uniqueness-only identifiers from secrets, while recognizing when guess resistance is required.
7. Seek non-security use, test-only reachability, or secure replacement before finalizing.

## Evidence Standard
`vulnerable` requires a predictable/insufficient generator or output construction in a reachable security-sensitive use. Cite CWE-330 and the numbered generation/use line. If purpose or active branch is missing, use `inconclusive`.

## Counterevidence and False Positives
`java.util.Random` is not a security issue in non-security contexts. `SecureRandom` with platform defaults is generally counterevidence unless supplied code introduces deterministic seeding or unsafe reuse. A UUID may or may not be a secret; decide from its authorization role, not its format alone.

## Confidence and Stopping Rules
High confidence requires generator, transformation, security purpose, and reachable use. Do not speculate about provider internals absent evidence.

## Output Discipline
Choose explicitly among `vulnerable`, `not_vulnerable`, and `inconclusive`, and do not calculate or demonstrate predicted values.
